## この回でやること

AIにブラウザを操作させて、自分のサイトの動作確認・テストを自動化する体験をする。「たぶん動くはず」ではなく**「実際に開いて確かめた」をAIにやらせる**。

## Playwright MCPとは

- AIがテキストで返事するだけでなく、**実際にブラウザを開いて操作・確認できるようになる**MCPサーバー
- スクリーンショット（見た目）とアクセシビリティツリー（ページ構造）の両方でページを把握する
- 対象は[localhost](http://localhost)（開発中）でもVercel本番でもOK

## 手順

### 1. 動作確認・巡回（パターン①）

自分のブログの全ページをAIに巡回させ、リンク切れ・コンソールエラー・表示崩れを探させる。

### 2. レスポンシブ確認（パターン②）

スマホ幅・PC幅でスクリーンショットを撮らせて、崩れを指摘させる。

### 3. ユーザーフロー確認（パターン③）

「一覧→記事詳細→戻る」など実際の導線を操作させる。

### 4. 発展: E2Eテスト生成・デバッグ（パターン④⑤）

時間に余裕がある人向け。操作内容をE2Eテストコードに書き起こさせたり、コンソールログ・ネットワークリクエストからの原因調査をAIと一緒にやる。

## 使い方パターン

| パターン | 何をさせるか | 使いどころ |
| --- | --- | --- |
| ① 動作確認・巡回 | 全ページを巡回してリンク切れ・コンソールエラー・表示崩れを探す | 自分のブログの健康診断 |
| ② レスポンシブ確認 | スマホ幅・PC幅でスクショを撮らせて崩れを指摘させる | CSS調整の前後比較 |
| ③ ユーザーフロー確認 | 「一覧→記事詳細→戻る」など実際の導線を操作させる | 動的ルートの動作確認 |
| ④ E2Eテスト生成 | 操作させた内容を`@playwright/test`のコードに書き起こさせる | Vitest回（単体テスト）との対比でE2Eを学ぶ |
| ⑤ デバッグ | コンソールログ・ネットワークリクエストを読ませて原因調査 | 「動かない」ときの調査をAIと一緒にやる |

## ポイント・注意

- **URLと確認観点を具体的に指示する**（「見て」ではなく「〜を確認して」）
- ログインが必要なページやCAPTCHAは苦手
- 削除ボタンなど破壊的な操作は自分で触らせない・実行前に確認させる

## そのまま使えるプロンプト集

```
① localhost:3000 を開いて、トップから辿れる全ページを巡回して。
   リンク切れ・コンソールエラー・表示崩れがあれば一覧で報告して。

② トップページを幅375pxと1280pxでスクリーンショットを撮って、
   レイアウトが崩れている箇所を指摘して。

③ 記事一覧ページから最初の記事をクリックして、詳細ページに
   タイトル・本文・日付が正しく表示されているか確認して。

④ いまの「一覧→詳細」の確認操作を @playwright/test のE2Eテストとして
   tests/blog.spec.ts に書いて。実行して通ることも確認して。

⑤ ○○ページで画像が表示されない。開いてコンソールとネットワーク
   リクエストを確認して、原因を調べて。
```
